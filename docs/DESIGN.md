# 设计说明

## 1. 产品定位

`mm-suno-creator` 负责创作前和生成阶段：把主题、歌词草稿或模糊风格描述转换成结构化 Suno 生成包。它不处理完成后的音频混音、分轨、母带或来源鉴定；这些任务属于独立项目 `mm-ai-music-refiner`。

## 2. 设计目标

- 降低不熟悉乐理、编曲和平台标签的创作者使用门槛；
- 让歌词、Style、Exclude、参数和时长约束彼此一致；
- 让每条标签的意义、组合关系与证据状态可查询；
- 用生成前检查减少超长、冲突、咬字困难和风格漂移；
- 保留稳定版本，以单变量方式解释下一轮生成结果。

## 3. 核心流程

```text
用户想法
  ↓
创作简报：主题 / 语言 / 主曲风 / 情绪弧 / 人声 / 时长 / 禁止项
  ↓
歌曲结构与段落时间预算
  ↓
可唱歌词：中文 / 英文 / 双语分别审核
  ↓
Style 装配：主轴 + 辅轴 + 律动 + 人声 + 乐器 + 制作 + 情绪
  ↓
Lint：长度 / 重复 / 冲突 / 曲风堆叠 / Exclude 对撞
  ↓
十段式生成包 + 下一轮单变量计划
```

## 4. 为什么采用 Skill + 查询脚本

`SKILL.md` 只保存高频决策流程，避免大型词典占用全部上下文。标签数据存放在 `assets/tags.json`，由确定性脚本完成查询、校验和报告。这样可以独立更新知识数据，也能让输出被测试和复现。

```text
skills/mm-suno-creator/
├── SKILL.md                 # 决策与交付流程
├── agents/openai.yaml       # Codex 展示信息
├── references/              # 按需加载的创作规则
├── assets/tags.json         # 标签单一事实源
└── scripts/                 # 查询、Lint、歌词分析、生成包
```

## 5. 数据与证据设计

每个标签包含规范 ID、中英文名称、别名、分类、定义、听感、适用场景、可组合项、冲突项、证据等级和核验日期。

证据等级不等同于平台保证：

- `curated_music_term`：音乐含义稳定，平台执行仍可能变化；
- `supported_observed`：存在带日期和版本的重复观察；
- `experimental`：行为不稳定，不作为默认高权重标签；
- `unknown`：信息不足，进入待核验队列，不编造。

## 6. 标准输出契约

完整任务始终交付：创作简报、可粘贴歌词、精简 Style、标准 Style、Exclude、参数理由、结构时长预算、标签释义、风险检查、下一轮单变量计划。命令行脚本输出 JSON 或 Markdown，避免依赖自由文本解析。

## 7. 关键取舍

- 不承诺标签能确定性控制生成模型；
- 不固定声称某个字符数是当前官方限制，Lint 预算可在运行时覆盖；
- 不用自动生成的空洞条目凑词典规模；
- 不把逐字双语翻译当作可唱歌词；
- 不操作账号、购买、发布或接受外部条款；
- 不模仿可识别旋律、歌词、声音或在世艺人的独特风格。

## 8. 版本路线

- `v0.1.x`：稳定创作工作流、种子词典、脚本接口和测试；
- `v0.2.x`：扩展高频核验标签、组合模板和中英文歌词规则；
- `v0.3.x`：加入带来源的模型版本适配记录与案例反馈导入；
- `v1.0.0`：达到生产词典覆盖、稳定迁移机制和完整回归集。

路线描述方向，不代表未发布能力已经可用；实际交付以 [CHANGELOG](../CHANGELOG.md) 为准。
